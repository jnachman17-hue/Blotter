## Build-specification production rule

A dedicated build specification is required when a surface contains presentation, state, interaction, mapping, or responsive decisions that cannot be implemented reliably from the cumulative WS4 or WS3 specification alone.

A build specification:

- is written after substantive questions are resolved with Jon;
- is self-contained and avoids chat-dependent shorthand;
- distinguishes exact requirements from bounded implementation discretion;
- records what to preserve, change, remove, and avoid;
- contains preview-review acceptance criteria;
- may govern a visual reference without turning the reference into a pixel-perfect target;
- becomes binding only when marked `Ratified`.

Do not create a separate build specification merely because a section contains ordinary text hierarchy. Conventional text, statistics, accordions, disclosure tables, CTA blocks, and simple layouts may be implemented directly from WS4 unless a specific ambiguity or failure justifies a dedicated specification.

## Visual-reference production rule

External visual-reference production remains limited to complex, implementation-sensitive assets where a visual guide materially reduces ambiguity.

A visual reference:

- supplements the written canonical specifications;
- may establish structure, hierarchy, exact data, and visual grammar;
- is not automatically a final website design or pixel target;
- must be accompanied by authoritative, directional, defect, and exclusion notes;
- exists to reduce ambiguity, not to create a second full design process outside Lovable.

Any additional external-reference work requires a specific implementation reason and Jon approval. No old reference proposal is automatically active.
